# 样板上传迁入 7.3.1：源码索引与重构方案

调查日期：2026-10-27。范围是本仓库 `main` 上的“从 ME 编码终端上传实体样板”，目标是本仓库的 `7.3.1` 分支；`7.3.1` 在这里是 ECO 分支名，不是 Minecraft 或 GTNH 整合包版本。

建议保留旧功能的交互意图，重写上传服务、目标适配和会话边界，再接入现有原生平台。旧代码包含可借鉴的兼容细节，但不适合整包复制或直接合并旧实现。

本文是设计交付，尚未实现上传功能，也未进行构建或游戏内验证。表中的“已确认”指源码事实；由该事实推导出的故障场景仍需对应测试或运行复现。

P0 场景是源码可构造的故障路径，不代表已在当前真实存档复现。旧代码已经有同网络检查、源样板快照比较、部分失败恢复和服务端任务调度；重构应补足这些边界，不能把旧实现描述成完全没有校验。

旧上传目录仅有 L24 两个 RecipeMap 字符串测试。上传、撤回、目标发现、机器切换、并发操作、电路和异常库存没有对应的上传专项测试，旧版本构建成功不能证明这些路径正确。

## 5. 建议的行为契约

以下是建议在实现前固定的产品规则；与旧实现不同的地方应在实现提交中明确说明。

1. **实体样板守恒。** 默认每次操作移动一张已编码样板。源槽若有多张，应保留余量；不得把一整堆塞入上限为 1 的目标。不会覆盖已有目标槽，也不会改写样板 NBT 来强行适配机器。
2. **空白样板只由 AE2 编码过程消耗。** 上传已有样板不再编码；右键编码准备上传时，只在确认本次编码成功后进入上传流程。失败沿用 AE2 状态，不上传旧输出。
3. **合成与处理分开。** ECO 合成总线仅接收合成样板。GT、普通 ME 接口、二合一接口按实际能力接收处理样板。零输出、隧道等特殊样板默认不进入自动路由，未经适配时给出明确原因。
4. **手动选择和自动决定分开。** 建议手动列表展示物理上可放入该样板的目标，并标出“精确匹配／电路冲突／未识别路由／已满／重复／离线”；未知机器可以由用户手动选择普通接口，自动上传只使用已验证路由。旧实现更严格地隐藏部分未知目标，这是需要明确记录的行为调整。
5. **电路提示只作有时效的来源信息。** 实体样板中的电路、NEI 上下文电路、机器配置电路、编程电路携带的目标值、空编程电路重置标记分别建模。发生冲突时禁止自动决定，不以“先找到的电路”为准。
6. **候选配方与机器可执行性分开。** 路由精确匹配说明配方与目标配置相符，不承诺机器当前电压、温度、催化剂、特殊槽和加工空间全部满足。无法证明的特殊语义显示原因，不把普通配方查询结果宣称为已能执行。
7. **自动排序稳定。** 建议合成样板优先可用 ECO 样板域，其次有已确认组装机能力的接口；处理样板优先精确配方／电路匹配，再按明确的用户／接口优先级、稳定位置键决胜。所有候选先通过可写校验；不同配方或不同电路存在歧义时进入列表，不靠任意遍历顺序自动上传。等价的同配方多机器可以稳定选择。
8. **重复范围明确。** 普通接口默认按目标库存判断实体样板重复；ECO 默认按 `getPatternDomain()` 去重，交换组中同域的总线合并显示，但执行仍落到具体物理槽。不同域可以各有一份样板。按物品 ID／meta／NBT 判断，上传去重时仅忽略样板顶层的 `encodedAt` 编码时间戳，不修改原始样板；物品转移、堆叠与撤回仍按完整 NBT 校验。是否忽略 author 等其他字段留给后续独立设计。
9. **可撤回必须有回执。** 上传成功后返回源、目标、物理槽、完整样板快照及版本；只有仍然满足前置条件才能撤回。源槽被占、目标被改、宿主更换、权限撤销时给出具体原因。自动上传成功也保留可访问的最近回执，解决旧自动成功直接返回后没有明确撤回入口的问题。
10. **会话结束释放引用。** 普通关闭、退出服务器、换世界及超时应清理玩家、库存、世界引用和客户端提示；只有已登记的“从终端切到上传页”过渡可以延续源访问凭据。一次操作的重复请求返回同一结果，不再次移动物品。

## 6. 模块划分与数据流

建议的目录和类名是后续实现落点，不表示这些类已经存在；可以合并很小的数据类，避免只为分层制造空接口。

```text
crafting/upload/
  model/       EncodedPatternSnapshot, PatternFingerprint, RouteHint,
               TargetKey, RouteCandidate, MatchResult, UploadReceipt
  service/     PatternUploadService, PatternUploadTransaction,
               PatternUploadSession, PatternUploadSessionRegistry,
               PatternTargetSelector
  spi/         PatternUploadAdapter, PatternSlotAccess, PatternRouteProbe

platform/ae2/upload/
  Ae2TerminalAccess, Ae2InterfaceUploadAdapter, EcoPatternBusUploadAdapter,
  NativePatternTargetCache
platform/gt/upload/
  GtPatternUploadAdapter, GtRecipeRouteProbe, GtRecipeMatcher
compat/ae2fc/upload/       二合一接口的身份与能力补充
compat/proghatches/upload/ 编程电路、覆盖板与样板映射库存
compat/gtnl/upload/        超级样板总成的物理槽边界
compat/nei/               GtPatternRouteCapture

  NativePatternUploadFactory, NativePatternUploadSession,
  NativePatternUploadPages, NativePatternUploadSnapshot
```

核心 `model/service/spi` 不出现 `gregtech.*`、可编程仓室或 GTNL 类型。平台适配器负责从真实对象提取信息；客户端只接收快照及服务端分配的 token，不通过坐标、下标或 NBT 任意指定可写库存。

一次查询的建议数据流：

```text
终端及编辑状态
  -> EncodedPatternSnapshot + 有效 RouteHint
  -> 网络中的目标描述及当前机器路由
  -> MatchResult {级别、原因、电路来源、所选路由、可写状态}
  -> 同一结果供列表、自动提示和自动选择使用
  -> 用户点击或自动操作
  -> 重新解析目标、复核版本与权限
  -> PatternUploadTransaction
  -> UploadReceipt / 明确的失败原因
```

`TargetKey` 至少区分 Mod 适配器、维度、坐标、线缆部件面和库存标识。同一坐标上的不同部件不能合并。键用于定位，不足以证明宿主未被替换；执行时还必须验证宿主身份或服务端分配的代次。

`PatternFingerprint` 绑定实体物品和完整 NBT；数量另行记录。`RouteHint` 绑定终端会话、编辑版本、配方输入输出摘要、来源及到期时间，不能作为网络写入授权。`MatchResult` 应一次性返回选定的路由及理由，避免旧版列表、tooltip、`selectRoute()`、`isExactMatch()` 各自推导出不同结果。

## 7. 事务、会话与窗口接入

### 7.1 上传和撤回共用的事务

所有步骤在当前 `ServerTasks.Session` 所属的服务端 tick 执行；异步工作只允许处理脱离世界的不可变数据。

1. 验证玩家、终端凭据、当前窗口、网络身份、AE2 实时权限和操作序号。样板库存编辑检查 `ISecurityGrid.hasPermission(player, SecurityPermissions.BUILD)`，并遵守目标适配器额外的宿主访问规则；不能以可读取终端代替可编辑样板。
2. 重新定位源槽与目标物理槽，读取源样板和机器配置，复核目标代次、槽容量、重复策略和路由。
3. 保存源／目标前态，使用已审计适配器提取一张到操作暂存，读回源槽，确认实际取出量。
4. 写入目标并读回完整物品与数量；执行该目标所需的脏标记、样板变更通知和菜单同步。
5. 两端达到预期后才生成成功回执。确认完全未写入时才能恢复源；部分写入、拒绝回滚或回调异常时先确定实际物品归属，禁止盲目恢复一份或自动重试。
6. 撤回按回执反向执行同一协议，只处理原物理槽和原样板；发现变化时停止，不搜索另一张相同样板来替代。

对任意未知 `IInventory`，仅凭 `setInventorySlotContents()` 的返回不能保证跨库存原子性。首版应只开放验证过的适配器；结果分为 `SUCCESS`、`REJECTED`、`INDETERMINATE`。不确定结果保留前后状态及操作号用于核查，不报告成功、不凭空补发。

该设计覆盖正常 tick、重复请求和可恢复异常。两个不同 Tile 的保存不是一个磁盘事务，服务器崩溃时的跨区块原子恢复不能由内存回执保证；若将它列为发布要求，需要另加持久化转移日志、保存顺序和恢复测试，不能随口宣称“崩溃也不丢”。

### 7.2 终端到 MUI2 页面的生命周期

M01 固定版本 `GuiManager.open():71–98` 会构造新页面、调用 `player.closeContainer()`，然后替换 `player.openContainer`。因此：

- 不能把“源 AE2 容器关闭”一律当成用户取消，否则正常打开上传页就失效。
- 也不能继续把旧 AE2 容器对象当成正在打开的容器；使用显式 `TERMINAL -> OPENING_UPLOAD -> UPLOAD_PAGE` 过渡，并绑定新窗口身份。
- 源访问凭据按有线 Tile、线缆部件、无线物品分别实现；无线物品位置、权限和保存回写需要独立验证。
- 上传页不能原样继承要求“一个 Tile、同世界、8 格距离”的 `NativeTileSession`。提取其队列和归属检查思路，建立面向终端凭据的会话。
- `NativeLateMixins` 按已加载 Mod 和物理侧启用对应桥；GUI／NEI 的客户端类不能出现在专服加载路径。
- 旧 GUI 注入涉及原版 `initGui`、`mouseClicked`、`actionPerformed`。应核对实际 Forge GUI 事件是否能满足交互；确需 Mixin 时提供正确的映射／refmap，并用重混淆安装 JAR 验证。不能因为 `remap=false` 的其它平台 Mixin 可用就照抄。

### 7.3 发现与缓存

通过 AE2 的接口终端注册类、网络节点和适配器识别候选；GT 特殊宿主可以从该网络节点的位置定向解析真实 MetaTileEntity。X07 的固定 AE2 实现中，`AENetworkProxy.getMachine()` 返回宿主 `gp`，不能把旧注释里“有时返回 proxy”的说法当成所有版本都必须扫描世界的证据。

GT 多方块归属需要额外索引：优先维护已成型控制器与其 `mDualInputHatches` 的映射；若第一阶段只能读取既有对象列表，允许在有界的初始化／失效重建中按世界扫描一次，再缓存结果，不能每个候选、每次 tooltip 都再扫描。模式、电路、覆盖板变化未必触发 AE2 样板事件，需要独立失效来源或有界刷新，并始终在提交前现场复核。

可借鉴 C10 的节点增加、删除、网络拆分／合并及样板事件。目标索引应独立于规划器缓存，避免一次上传查询牵动整个合成规划。查询缓存按网络版本、样板指纹、来源提示和目标配置版本关联；只缓存位置、版本或有明确生命周期的句柄。

## 8. GT 与扩展 Mod 的适配规则

| 目标 | 源码依据 | 实现要求 |
| --- | --- | --- |
| 普通 ME 接口／部件 | X01、X04 | `IInterfaceViewable.getPatterns()` 和物理样板槽；位置键包含部件面；图标用于展示，不作为机器路由证明 |
| 原生 GT ME 样板输入总成／总线 | G01–G03 | 固定版本同一个 `MTEHatchCraftingInputME` 用 `supportsFluids()` 区分，36 个物理样板槽；`getPatterns()` 返回整机库存，后面还有电路／手动槽，不能使用整个库存大小 |
| GT 多方块归属 | G02–G03 | 固定 GT 版本确实有 `processingLogics`；控制器公开 `mDualInputHatches`。把必要的受保护访问集中在一个经过版本检查的桥，不在核心到处反射 |
| AE2FC 二合一接口 | A01–A02 | 继承原生接口但要识别实际类型和流体能力；普通接口不能只凭父类或图标被误标成二合一接口 |
| 可编程仓室 | P01–P03 | `getPatterns()` 返回独立 `patternMapper`；`setInventorySlotContents()` 有 `onPatternChange()`，而 mapper 的 `markDirty()` 为空。写入适配器需要确认宿主保存及发布语义，不能只调用通用 markDirty |
| 编程覆盖板 | P02–P03 | 空目标是重置语义；覆盖板可设置多个电路槽。不能只检测任意面上存在该类就断言当前输入路径具有全部编程能力 |
| GTNL 超级样板输入总成 | N01 | 当前参考源码 `MAX_PATTERN_COUNT=360`，`rows()` 动态报告占用附近的显示行，库存随后是电路及 81 个手动槽。按锁定版本的实际槽边界适配，不能硬套 `rows()*rowSize()` 或整机库存大小 |

GT 配方匹配分两步：先用原生配方查询缩小候选，再复核样板承诺的物品／流体数量、统一的执行倍率、NBT、电路角色和该配方需要的特殊信息。物品和流体倍率必须一致；数量计算保留 long 或 BigInteger，不先截断到 int。矿辞替代和流体身份按 GT 真实匹配规则处理。

“2 个 A -> 1 个 B”与“20 个 A -> 10 个 B”可以是同一配方的批量；“20 个 A -> 1 个 B”不能仅因种类相同就认定为等价。未列入样板的副产物是否允许应遵循配方和执行端规则；概率输出不能未经处理当作确定产出。需要特殊槽、研究数据或多模式选择而无法验证时返回 `UNVERIFIED`，不给自动上传的确定性结论。

NEI 捕获必须对照实际 transfer 路径。L05 只挂在 AE2 的 `NEICraftingHandler.overlayRecipe()`；不同终端、GT 与 AE2FC 的提取／填充路径不能假定都经过这里。G05 当前页面的 `arecipes[recipeIndex]` 与全局缓存顺序不同，不能在分级或搜索后按相同下标回退到另一份缓存来猜电路。无法读取时清除提示并交给服务端重新验证。

可编程仓室和 GTNL 这里仅锁定了源码参考提交，尚未锁定用户整合包中的实际安装 JAR。将它们纳入支持清单前，需要补齐安装版本和发布 JAR 契约检查；不能把最新源码调查直接当作对任意旧安装版本的兼容保证。

## 10. 验收矩阵

| 类别 | 最小场景 | 通过标准 |
| --- | --- | --- |
| 数量与事务 | 正常上传／撤回；多张源；目标已满；拒写／部分写入／异常／清理失败 | 无覆盖、无盲目补发；总量及归属可核对；不确定结果明确阻止重试 |
| 请求与会话 | 连点、重复序号、旧请求晚到、关闭、断线、服务器重启／换世界 | 一次物品转移最多成功一次；旧会话不能作用于新世界或新窗口 |
| 源合法性 | 源样板改写、权限撤销、源终端替换、部件面不同、无线物品换槽 | 提交前拒绝失效凭据；不得写错目标或错误回写无线物品 |
| 目标合法性 | 上传页打开后目标拆除、区块卸载、断网、网络拆分、机器改模式／电路 | 快照失效可见；执行重新确认宿主、网络及路由 |
| 配方语义 | 合成／处理、手动／NEI、物品／流体、正确倍增／错误倍率、NBT、特殊与概率产物 | 列表、自动提示、提交共享同一判断；未验证语义不伪装精确匹配 |
| 电路 | 普通／虚拟／编程电路、空重置、覆盖板、多电路、来源冲突 | 电路来源可解释；冲突不自动选；不把非消耗输入计成普通消耗倍率 |
| ECO 样板域 | 单主机、多总线、同交换组、不同组、域拆分／重组 | 按当前域去重；可见范围来自 `getPatternDomainBuses()`；落到真实空槽 |
| 适配边界 | 无 GT、GT 原生舱室、AE2FC、可编程仓室、GTNL | 可选依赖缺失可加载；只写样板槽；变更后能保存并刷新发布 |
| UI 与规模 | 0／1／127／128／更多目标、搜索／分页、窗口缩放、切终端、客户端语言不同 | 所有目标可达；选择使用 token；无旧提示串窗；定位区分维度与部件 |
| 成本 | 多玩家打开终端、大网络、多个 GT 多方块 | 记录目标数、重建数、查询耗时和扫描次数；热提示查询不新增全世界扫描 |

自动检查在实现后执行，以下是计划命令，不是本次已执行的验证结果：

```powershell
# 先运行新增的上传测试；实现时按最终类名调整过滤器。
./gradlew.bat test --tests '*PatternUpload*' --tests '*PatternRoute*' --offline --console=plain

# 然后执行正常完整检查，含现有重混淆库存验证。
./gradlew.bat test build --offline --console=plain

# GT 环境另外核对实际运行依赖。
./gradlew.bat verifyGtRuntimeProfile --offline --console=plain
```

不加载 GT 的契约需要独立无 GT 运行 classpath／类加载测试。仅加 `-PgtRuntime=false` 不足以证明这个性质，因为项目测试依赖本身仍可能传递带入 GT 类。可选适配器的安装包验证也要使用真实解析的运行 JAR，而不是只有源码检查。

测试／构建、重混淆安装包检查、真实客户端操作、专服与可选 Mod 组合运行分别留证。只有进入世界并完成对应鼠标动作后，才能称相应交互已通过；本次没有启动游戏，也没有调用 mcpfabric。

## 11. 推荐落地范围

第一批实现 R0–R3：完成可靠的单张转移、普通 ME 接口、ECO 合成样板域及原生 GT 路由，保留一个可用的手动页面。随后完善自动交互和无线终端，再逐个恢复扩展 Mod。

恢复前应补齐的外部输入只有扩展 Mod 的实际安装版本及用户能稳定复现的旧 bug 操作。它们不妨碍先实现核心事务和原生目标，但未核实的终端／扩展组合应保持“待验证”，不能继承旧代码的支持声明。
